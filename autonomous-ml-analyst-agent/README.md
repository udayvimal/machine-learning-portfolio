# Autonomous ML Analyst Agent

> A LangGraph agent that performs end-to-end ML analysis on a raw CSV it has never seen before —
> deciding the target variable, engineering features, training models, and critiquing its own results
> without any human-provided labels or pipeline instructions.

---

## Key Results

What makes this different from a standard ML project:

| Aspect | Standard ML notebook | This agent |
|---|---|---|
| Target column | **Hardcoded by human** | **Agent discovers it** from column names + cardinality |
| Problem type | **Declared up front** | **Agent decides** classification vs regression from evidence |
| Feature encoding | **Fixed pipeline** | **Agent adapts**: OHE for low-cardinality, ordinal for high, imputation strategy based on missingness |
| Model selection | **Pre-chosen** | **Agent reasons** about dataset size + structure, trains 3 candidates, compares |
| Failure detection | **Rarely done** | **Agent flags** leakage, overfitting, and class imbalance as part of the pipeline |

Run results across four structurally different datasets:

| Dataset | Problem type | Agent's target choice | Best model | Score |
|---|---|---|---|---|
| Customer Churn (clean) | Classification | `churned` (correct) | GradientBoostingClassifier | F1=0.81 |
| Housing Prices (clean) | Regression | `sale_price` (correct) | Ridge | R²=0.96 |
| Employee Attrition (messy, ~20% missing) | Classification | `left_company` (correct) | RandomForestClassifier | F1=0.77 |
| Customer Churn + Leakage Column | Classification | `churned` (correct) | LogisticRegression | F1=1.00 (LEAKAGE) |

On the leakage dataset, the agent correctly achieved F1=1.00 and **correctly flagged it as suspicious** in the critique node, identifying `risk_assessment_score` as encoding the target.

## Agent Architecture (LangGraph Node Flow)

```
CSV input (no metadata — raw file only)
         |
         v
+--------------------+
|   DATA PROFILING   |  Loads CSV. Computes shape, dtypes, missing rates,
|    (Node 1/6)      |  distributions, skew, binary column correlations.
+--------------------+
         |  profile_stats, profile_text
         v
+--------------------+
|  PROBLEM FRAMING   |  Decides: which column is the target?
|    (Node 2/6)      |  Is this classification or regression?
+--------------------+  Uses column naming + cardinality + dtype evidence.
         |  target_col, problem_type
         v
+--------------------+
|  FEATURE           |  Plans encoding strategy from profile evidence.
|  ENGINEERING       |  Executes via sklearn ColumnTransformer:
|    (Node 3/6)      |  - Numeric: median imputation + StandardScaler
+--------------------+  - Categorical: mode imputation + OneHotEncoder
         |  X_engineered, feature_names
         v
+--------------------+
|  MODEL SELECTION   |  Trains 3 candidates with 5-fold CV.
|  & TRAINING        |  Classification: LR / RandomForest / GBM
|    (Node 4/6)      |  Regression: Ridge / RandomForest / GBM
+--------------------+  Reports CV score, test score, feature importance.
         |  model_results, best_model, best_score
         v
+--------------------+
|  CRITIQUE NODE     |  Reviews results for failure modes:
|    (Node 5/6)      |  - Overfitting (train/test gap > 0.15)
+--------------------+  - Data leakage (feature importance > 50% single feat)
         |  critique_text, leakage_warning, overfitting_warning  |  - Target correlation > 0.85 in profiling
         v
+--------------------+
|  REPORT GENERATION |  Writes full plain-English analysis report.
|    (Node 6/6)      |  Includes all node outputs + honest caveats.
+--------------------+
         |
         v
  final_report.md + full_transcript.md
```

## Example Agent Reasoning Output

The following is **actual text generated by the agent** on the leakage dataset (Run 4), not paraphrased:

### Node 2 — Problem Framing (leakage dataset)
```
**Problem framing analysis**

I examined all 10 columns for naming patterns, cardinality, and data type to identify the
prediction target.

**Selected target column**: `churned`
Reasoning: `churned` has 2 unique values. Low cardinality with a discrete domain ->
classification.

**Problem type**: CLASSIFICATION

**Input features** (9 columns):
`age`, `tenure_months`, `monthly_charges`, `num_products`, `support_tickets`,
`has_premium`, `contract_type`, `payment_method`, `risk_assessment_score`

**Dataset scale**: 450 rows is sufficient for training non-linear models.

[!] **Preliminary leakage flag**: columns with correlation >0.85 with the target were
detected during profiling. This warrants scrutiny in the critique phase.
```

### Node 5 — Critique (leakage dataset)
```
**Agent critique of model results**

**Issues flagged**:
  **[LEAKAGE] Data leakage risk**: the following features have correlation >0.85 with
  `churned`: {'risk_assessment_score': 0.968}. These likely encode the target directly
  (e.g., derived from it post-event, or computed from the outcome). Remove and retrain
  before trusting the scores.

  **[!] Single-feature dominance**: one feature accounts for 97.3% of total importance.
  This concentration is atypical and may signal leakage or a proxy target — investigate
  before deployment.
```

### Node 3 — Feature Engineering (messy dataset)
```
**Feature engineering plan — with rationale for each decision**

Numeric features (6): age, years_at_company, last_promotion_years, wfh_days_per_week,
performance_rating, ...
  -> SimpleImputer(strategy='median'): robust to outliers; median preferred over mean
  when distributions are skewed.
  -> StandardScaler: zero-mean, unit-variance scaling required for LogisticRegression/
  Ridge to converge properly. Tree models are scale-invariant but scaling does no harm.

Categorical features (3): department, job_role, salary_band
  -> OneHotEncoder(handle_unknown='ignore') on [...]: low cardinality makes OHE tractable;
  'ignore' for unseen values at inference.
  -> SimpleImputer(strategy='most_frequent'): fills rare NaN gaps with the modal category.

Missing values present in 5 column(s): {'last_promotion_years': 18.0, 'wfh_days_per_week':
22.0, 'performance_rating': 12.0, 'age': 5.0, 'salary_band': 8.0}
```

## Where This Agent Gets It Wrong

### What we did to test failure modes

Dataset 4 was deliberately constructed with `risk_assessment_score = churned * 82 + noise`.
The column name sounds like a legitimate business feature (it could plausibly be a
credit-risk score computed before the customer decision). The agent was run blind.

### What the agent got right
- Detected `risk_assessment_score` had 0.968 correlation with `churned` during profiling
- Raised a preliminary leakage flag in the problem framing node
- Identified single-feature dominance (97.3% importance to that column) in the critique
- Correctly escalated to `[!] LEAKAGE WARNING` in the final report

### What the agent got wrong / limitations

1. **It still trained models including the leaky feature** — it flagged the issue but did
   not automatically drop the feature and retrain. A more sophisticated agent would loop
   back to feature engineering with leaky columns removed.

2. **The target inference heuristic is keyword-based** — in mock mode, the agent uses
   column name matching to find the target. For columns with non-obvious names (e.g.,
   `y`, `outcome_v2`, or obfuscated labels), it falls back to the last column which may
   be wrong. With a real LLM (Groq), this reasoning is much richer.

3. **No hyperparameter tuning** — the agent trains default-configuration models. It
   reasons about which model type to use but doesn't tune. A production version would
   add an Optuna node after model selection.

4. **Regression leakage detection is weaker** — for linear models, feature importances
   are raw regression coefficients (not in [0,1]), so the single-feature dominance check
   is disabled for Ridge. Leakage in regression requires a different check (e.g., feature
   correlation with target).

5. **No temporal structure awareness** — the agent doesn't detect time-series patterns
   or warn about train/test leakage from future data being used as features.

## Quick Start

```bash
# 1. Clone and install
git clone https://github.com/udayvimal/machine-learning-portfolio
cd machine-learning-portfolio/autonomous-ml-analyst-agent
pip install -r requirements.txt

# 2. (Optional) Add Groq API key for real LLM reasoning
cp .env.example .env
# Edit .env: GROQ_API_KEY=gsk_...
# Without this, the agent runs in data-driven mock mode (all ML is real; reasoning is rule-based)

# 3. Generate all 4 evaluation datasets and run the agent on each
python generate_all_runs.py

# 4. Run on your own CSV
python run_agent.py path/to/your/data.csv --run-name "My Analysis"
```

## Tech Stack

| Layer | Technology |
|---|---|
| Agent orchestration | LangGraph (StateGraph, 6 nodes, linear flow) |
| LLM reasoning | Groq API — Llama 3.3 70B (optional; mock mode if no key) |
| ML execution | scikit-learn (ColumnTransformer, Pipeline, CV), XGBoost |
| Feature engineering | StandardScaler, OneHotEncoder, SimpleImputer |
| State management | LangGraph TypedDict AgentState |
| Data generation | NumPy / pandas (4 synthetic datasets with controlled properties) |
